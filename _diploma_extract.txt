  67|Heading 3               |1.2.3 Сравнение функциональности
  68|Документация            |По шкалам настроения, стресса и энергии в диапазоне 1–10 полный набор реализован только в Serenity; Daylio и Sanvello ограничиваются в основном настроением или опросниками, eMoods — преимущественно настроением, MindDoc — структурированными опросами, Moodnotes — текстовым дневником без трёх количественных шкал.

  70|Документация            |История с фильтрацией доступна в Daylio, eMoods, Moodnotes и частично в Sanvello; календарное или тепловое представление настроения — в Daylio и eMoods, в Serenity — на экране History (режим календаря).   72|Документация            |Редактирование записей поддерживают Daylio, eMoods, Moodnotes; в Serenity дополнительно зафиксировано в REST (PUT /mood/{id}). Собственный REST API на FastAPI и хранение журнала в PostgreSQL — отличительные черты учебного проекта; аналоги используют проприетарные backend без передачи разработчику полного стека.
  73|Документация            |Локально на устройстве в Serenity через SharedPreferences сохраняются язык, тема и данные по советам; журнал настроения на сервере не дублируется в локальной СУБД. У коммерческих приложений локальные настройки также применяются, но синхронизация и учётные записи, как правило, встроены в облачную инфраструктуру; в Serenity регистрация пользователей в MVP не реализована.

  77|Heading 3               |1.2.5 Отличия разрабатываемого приложения Serenity
  78|Документация            |Разрабатываемое приложение Serenity (проект Mood Monitor) отличается от перечисленных аналогов следующим.
  79|Документация            |По архитектуре записи о настроении, стрессе и энергии хранятся на сервере в PostgreSQL; клиент на Flutter получает и изменяет данные через REST API.   82|Документация            |Ограничения MVP осознанные: нет регистрации пользователей, офлайн-синхронизации журнала и push-уведомлений; список записей загружается целиком с сервера. Это согласуется с учебным характером работы и не дублирует возможности зрелых аналогов.
  83|Документация            |Таким образом, обзор аналогов подтверждает актуальность темы диплома и обосновывает выбор функций, реализованных в Serenity и описываемых в главах 2–3.

 123|Heading 3               |1.3.5 Требования к клиентской части (Flutter)
 124|Документация            |Клиент должен реализовать экраны Dashboard, добавление и редактирование записи, History (список, календарь, аналитика), Recommendations, Settings, детали совета и таймер дыхания. Доступ к API — через единый класс ApiService с обработкой таймаутов и ошибок. Журнал записей на устройстве не дублируется в локальной СУБД: данные запрашиваются с сервера при открытии экранов и обновляются после сохранения (в том числе перезагрузка Dashboard после Add Mood).  125|Heading 3               |1.3.6 Требования к серверной части (FastAPI) [15].
 126|Документация            |Сервер на Python с фреймворком FastAPI должен принимать HTTP-запросы, выполнять бизнес-логику и обращаться к PostgreSQL через SQLAlchemy. Маршруты журнала — в routes/mood.py; прогноз и отзыв — в routes/diploma.py. При создании и изменении записи выполняется валидация полей схемами Pydantic. Список записей возвращается отсортированным по убыванию created_at. Расчёт индекса благополучия, текста рекомендации и прогноза выполняется в модулях wellbeing_service, recommendation_service и forecast_service. При старте в учебном режиме допускается создание таблиц через Base.metadata.create_all [16] [17].
 127|Heading 3               |1.3.7 Требования к СУБД PostgreSQL
 128|Документация            |В таблице mood_entries хранятся поля: id, mood, stress, energy, note, category, sleep_hours, activity_minutes, created_at. СУБД обеспечивает транзакционное сохранение при db.commit(). Допускается индекс по category для фильтрации. Резервное копирование выполняется средствами PostgreSQL вне приложения.  129|Heading 3               |1.3.8 Требования к REST API.
 130|Документация            |Сервер предоставляет следующие конечные точки. GET /health — проверка доступности сервиса, ответ 200. POST /mood — создание записи, ответ 201 с телом созданной записи. GET /mood — получение списка всех записей, ответ 200. GET /mood/{entry_id} — получение одной записи, ответ 200 или 404. PUT /mood/{entry_id} — обновление записи, ответ 200 или 404. DELETE /mood/{entry_id} — удаление записи, ответ 204 или 404. GET /wellbeing — индекс благополучия по последней записи, ответ 200. GET /recommendations с параметром lang — рекомендация, ответ 200. GET /forecast с параметрами user_id и lang — прогноз, ответ 200. POST /feedback — приём отзыва о совете, ответ 201.
 131|Документация            |Тела запросов и ответов соответствуют схемам Pydantic. Ошибки валидации возвращаются с кодом HTTP 422; отсутствие записи — с кодом 404. Интерактивная документация доступна по адресу /docs (Swagger UI).
 132|Документация            |Вывод по §1.3. Сформулированные требования описывают целостный контур мониторинга психоэмоционального состояния с серверным хранением данных и прозрачной серверной аналитикой. Они служат основой для описания архитектуры, реализации API (глава 2) и интерфейса приложения (глава 3). На этапе доработки диплома целесообразно согласовать введение и заключение с серверной моделью хранения (PostgreSQL, REST), без упоминания локальной PostgreSQL для журнала настроения.

 142|Документация            |В качестве основного инструмента для разработки API был выбран фреймворк FastAPI. FastAPI представляет собой современный веб-фреймворк, предназначенный для создания программных интерфейсов взаимодействия между различными компонентами системы. Он разработан специально для создания высокопроизводительных API и отличается высокой скоростью работы, удобством разработки и современным подходом к проектированию серверных приложений.
 143|Документация            |Одним из ключевых преимуществ FastAPI является его высокая производительность. Благодаря использованию асинхронной архитектуры и современного механизма обработки запросов данный фреймворк способен эффективно обрабатывать большое количество одновременных соединений. Это особенно важно для серверных приложений, которые должны обеспечивать стабильную работу при взаимодействии с множеством пользователей.
 144|Документация            |Еще одной важной особенностью FastAPI является встроенная поддержка автоматической проверки данных. При получении запроса от клиента фреймворк автоматически проверяет корректность передаваемых параметров и их соответствие ожидаемой структуре. Это позволяет предотвратить возникновение ошибок при обработке данных и повысить надежность программной системы.
 145|Документация            |Кроме того, FastAPI предоставляет удобные инструменты для описания структуры API и автоматической генерации документации. После разработки серверных обработчиков система автоматически формирует интерактивную документацию, которая позволяет разработчикам тестировать API-запросы и просматривать структуру доступных методов. Это значительно упрощает процесс разработки и тестирования серверной части приложения.
 146|Документация            |Серверная часть приложения выполняет несколько важных функций, связанных с обработкой данных и взаимодействием с клиентским приложением. Одной из основных задач сервера является обработка HTTP-запросов, поступающих от клиентского приложения. Клиентская часть программы отправляет запросы на сервер для получения или сохранения данных, после чего сервер принимает данные, выполняет необходимые операции обработки и формирует ответ, который передается обратно клиенту.
 147|Документация            |Помимо обработки запросов сервер отвечает за реализацию основной бизнес-логики приложения. Бизнес-логика определяет правила обработки данных, порядок их сохранения и методы взаимодействия между различными компонентами системы. В рамках данного проекта серверная часть обеспечивает прием данных о состоянии пользователя, их сохранение в базе данных и последующую передачу клиентскому приложению для отображения статистики и анализа.
 148|Документация            |Еще одной важной функцией серверной части является взаимодействие с базой данных. Для реализации данной возможности используется библиотека SQLAlchemy, которая представляет собой инструмент для работы с базами данных на языке Python. Данная библиотека обеспечивает удобный интерфейс для выполнения операций с данными и позволяет работать с различными системами управления базами данных.
 149|Документация            |SQLAlchemy реализует механизм объектно-реляционного отображения, который позволяет представлять записи базы данных в виде объектов программного кода. Такой подход значительно упрощает работу с данными и позволяет разработчику взаимодействовать с базой данных с использованием привычных конструкций языка программирования. Благодаря этому процесс добавления, получения, обновления и удаления данных становится более удобным и безопасным [18].
 150|Документация            |База данных используется для хранения информации о записях пользователя. Каждая запись содержит данные о состоянии пользователя в определенный момент времени. В системе сохраняются такие параметры, как уровень настроения, уровень энергии, уровень стресса, текстовая заметка пользователя и дата создания записи. Данные параметры позволяют сформировать подробную историю эмоционального состояния пользователя.
 151|Документация            |Наличие базы данных позволяет хранить большое количество записей и обеспечивать быстрый доступ к необходимой информации. При необходимости сервер может выполнять запросы к базе данных, извлекать нужные записи и передавать их клиентскому приложению для отображения статистики или построения графиков.
 152|Документация            |Хранение данных в базе данных также дает возможность анализировать изменения эмоционального состояния пользователя во времени. На основе накопленной информации приложение может строить графики изменения настроения, вычислять различные показатели и формировать рекомендации для пользователя. Это позволяет сделать приложение не только инструментом для фиксации данных, но и системой анализа эмоционального состояния.
 153|Документация            |Таким образом, использование языка программирования Python, веб-фреймворка FastAPI и библиотеки SQLAlchemy позволяет создать эффективную серверную часть приложения. Данные технологии обеспечивают обработку запросов клиента, надежное хранение информации в базе данных и реализацию бизнес-логики системы. Благодаря этому приложение способно стабильно функционировать, обрабатывать пользовательские данные и обеспечивать взаимодействие между различными компонентами программной системы.
 156|Heading 1               |2 Проектирование и реализация программной системы мониторинга настроения (интерфейс «Серенити»)
 157|Heading 2               |2.1 Архитектура системы
 158|Heading 3               |2.1.1 Общая клиент-серверная схема [19].
 159|Документация            |Разрабатываемая система мониторинга психоэмоционального состояния построена по классической трёхуровневой схеме: мобильный клиент, сервер приложений и сервер данных. Пользователь работает с кроссплатформенным приложением, интерфейс которого реализован на фреймворке для разработки пользовательских приложений; в учебной документации продукт обозначается как «Серенити», а репозиторий исходного кода — как система мониторинга настроения.
 160|Документация            |Клиент обращается к программному интерфейсу сервера по протоколу передачи гипертекста; сервер принимает запросы, проверяет корректность данных и выполняет операции с реляционной базой данных PostgreSQL через объектно-реляционное отображение SQLAlchemy. Такое разделение обеспечивает единый источник истины для журнала самочувствия: все записи об уровне настроения, стресса и энергии хранятся в таблице записей настроения на сервере, а не на устройстве пользователя.
 161|Документация            |На смартфоне или эмуляторе сохраняются только параметры, не относящиеся к журналу: выбранный язык интерфейса, тема оформления, списки избранных и скрытых советов, отметки о полезности рекомендаций и выполненных за день быстрых действий. Для этого используется встроенное локальное хранилище ключей и значений, доступное из модуля хранения локали и настроек. Расчёт индекса благополучия, текстов персональных рекомендаций и краткосрочного прогноза выполняется исключительно на сервере, что соответствует требованиям первой главы и исключает расхождение формул между платформами.
 162|Документация            |Обмен между уровнями ведётся в структурированном текстовом формате, принятом для веб-сервисов. Для учебного развёртывания допускается работа в локальной сети: базовый адрес сервера задаётся при сборке клиента. Учётные записи пользователей в текущей версии не вводятся; идентификатор пользователя в запросах зарезервирован для возможного расширения.
 163|Heading 3               |2.1.2 Серверная часть
 164|Документация            |Точка входа серверной программы — главный модуль приложения. При запуске создаётся экземпляр веб-фреймворка, подключается промежуточное программное обеспечение для разрешения кросс-доменных запросов при отладке, регистрируются маршруты из модулей журнала настроения и дополнительных учебных маршрутов, выполняется создание таблиц в PostgreSQL при отсутствии структуры. Служебный запрос проверки доступности возвращает признак готовности сервиса.
 165|Документация            |Модуль подключения к базе данных задаёт строку соединения: она считывается из файла настроек окружения, по умолчанию указывает на локальный сервер PostgreSQL и базу с именем, принятым в проекте. Создаются движок соединений, фабрика сессий и генератор зависимости, который выдаёт сессию на время обработки одного запроса и гарантированно закрывает её по завершении, что предотвращает утечку соединений.
 166|Документация            |В каталоге моделей описан класс записи настроения, отображаемый на таблицу записей настроения. Это единственная предметная сущность в схеме базы данных. В каталоге схем описаны контракты проверки данных: структура для создания и чтения записи, ответ с индексом благополучия, ответ с рекомендацией, ответ с прогнозом, структура для приёма отзыва о совете. Фреймворк автоматически проверяет входящие тела запросов и формирует ответы по этим описаниям.
 167|Документация            |Каталог маршрутов реализует тонкий сетевой слой. В модуле журнала сосредоточены создание, получение списка, получение одной записи, изменение и удаление записей, а также запросы индекса благополучия и персональной рекомендации; последние передают управление в модуль рекомендаций. В модуле учебных маршрутов — запрос прогноза и приём отзыва; отзыв в базе данных не обязан сохраняться.
 168|Документация            |Каталог сервисов содержит вычислительную логику. Модуль благополучия рассчитывает линейный индекс по весам настроения, энергии и стресса, зафиксированным в отдельном файле констант. Модуль рекомендаций формирует уровень тревоги и текст совета по последней записи с учётом высокого стресса, недостатка сна, категории «работа», низкой энергии и отсутствия активности. Модуль прогноза оценивает риск на следующий день по окну последних записей, не более четырнадцати; для показа числового прогноза требуется не менее трёх записей в журнале.
 169|Документация            |Таким образом, маршрут принимает запрос, получает сессию базы данных, при необходимости читает или изменяет объекты записи настроения, вызывает сервисы для аналитики и возвращает клиенту проверенную структуру ответа.
 170|Heading 3               |2.1.3 Клиентская часть
 171|Документация            |Клиент расположен в каталоге мобильного приложения. Главный модуль инициализирует форматы даты для русского и белорусского отображения, загружает сохранённые язык и тему, строит приложение с поддержкой светлого, тёмного и системного оформления.
 172|Документация            |Экран главной панели показывает индекс благополучия, график динамики настроения, блок практик и ежедневного опроса, цель недели по числу дней с записями, карточку последней записи и карточку прогноза. Экран добавления и пошагового потока ввода служат для создания новой записи. Экран редактирования изменяет существующую запись. Экран истории объединяет список с фильтрами, календарное представление с цветовой индикацией по дням и режим аналитики с графиками. Экран рекомендаций показывает серверный совет и локальный каталог статей по категориям. Экран настроек меняет язык и тему. Отдельный экран реализует таймер дыхательной практики.
 173|Документация            |Модели данных на клиенте отражают поля ответов сервера. Сетевой слой инкапсулирует все обращения к серверу. Виджеты оформления вынесены в отдельные компоненты для главной панели и истории. Конфигурация задаёт базовый адрес сервера в зависимости от платформы: для эмулятора Android используется специальный адрес доступа к компьютеру разработчика, для настольной отладки — локальный хост.
 174|Документация            |После успешного сохранения записи главная панель перезагружает данные: повторно запрашивается список записей, прогноз и связанные показатели. Нижняя панель навигации связывает главную панель, историю и рекомендации без глубокой вложенности меню.
 175|Heading 3               |2.1.4 Обмен данными через программный интерфейс [20].
 176|Документация            |Взаимодействие построено в стиле передачи состояния представления: ресурс записи имеет коллекционный адрес и адрес с идентификатором; агрегированные показатели вынесены на отдельные адреса индекса, рекомендации и прогноза. Создание сопровождается кодом ответа «создано», чтение — «успешно», удаление — «нет содержимого».
 177|Документация            |Класс доступа к серверу формирует полный адрес запроса, устанавливает заголовок типа содержимого для текста в формате обмена, кодирует тело запроса и разбирает ответ в объекты записи и прогноза. Установлен предельный интервал ожидания ответа; ошибки сети и коды отказа преобразуются в исключения с понятным сообщением для пользователя. Отдельный короткий запрос проверяет доступность сервера перед длительными операциями.
 178|Heading 3               |2.1.5 Локальное хранилище параметров интерфейса
 179|Документация            |Модуль хранения локали обращается к встроенному хранилищу параметров приложения. Сохраняются код языка, режим темы, множества идентификаторов избранных и скрытых советов, списки отмеченных полезных и бесполезных советов, а также отметки о выполненных быстрых действиях с привязкой к календарной дате. Журнал настроения таким способом не дублируется: при отсутствии связи с сервером пользователь по-прежнему может менять язык и просматривать ранее сохранённые настройки советов, но новые записи самочувствия без сервера не появятся в общей истории.
 180|Heading 3               |2.1.6 Поток данных при создании записи
 181|Документация            |При добавлении записи пользователь на экране ввода задаёт три обязательные оценки и при необходимости заметку, категорию, часы сна и минуты активности. По команде сохранения клиент формирует текст запроса и отправляет его методом создания ресурса на адрес журнала. Сервер проверяет диапазоны шкал и длину строк, создаёт объект записи, помещает его в сессию, подтверждает транзакцию в базе данных и возвращает полную запись с присвоенным идентификатором и меткой времени.
 182|Документация            |Клиент преобразует ответ в объект записи, показывает подтверждение и закрывает экран ввода. При возврате на главную панель выполняется повторная загрузка списка и запрос прогноза; индекс благополучия обновляется по последней строке в базе. Если это третья и последующие записи, на карточке прогноза появляется числовая оценка риска и пояснение на выбранном языке.
 183|Документация            |Вывод по разделу 2.1. Архитектура представляет собой согласованный контур «мобильный клиент — сервер приложений — PostgreSQL» с централизованным журналом и серверной аналитикой; разделение каталогов маршрутов, сервисов, моделей и схем упрощает сопровождение и описание в пояснительной записке.
 184|Heading 2               |2.2 Модель данных и база данных
 185|Heading 3               |2.2.1 Система управления базами данных PostgreSQL
 186|Документация            |PostgreSQL выбрана как промышленная СУБД с поддержкой транзакций, типов даты и времени с часовым поясом и индексов по отдельным столбцам. Для мобильного клиента важно, что сервер базы может работать на компьютере разработчика в локальной сети, а телефон обращается к нему по адресу в сети Wi‑Fi, что ближе к реальной схеме развёртывания, чем встраиваемая файловая база на устройстве.
 187|Документация            |Подключение задаётся строкой с указанием драйвера, учётной записи, хоста, порта и имени базы. Параметры переопределяются через файл окружения в каталоге сервера. Резервное копирование и восстановление выполняются штатными средствами СУБД вне приложения.
 188|Heading 3               |2.2.2 Таблица записей настроения и назначение полей
 189|Документация            |Все записи журнала хранятся в одной таблице. Столбец идентификатора является первичным ключом и автоматически увеличивается при вставке. Столбцы настроения, стресса и энергии обязательны; допустимые значения — целые числа от одного до десяти. Именно они входят в формулу индекса благополучия и в эвристики прогноза.
 190|Документация            |Столбец заметки имеет текстовый тип и может быть пустым: пользователь описывает события дня или причины состояния. Столбец категории хранит короткий тег контекста длиной до пятидесяти символов, например работа, отношения, здоровье; по нему строится фильтр на клиенте и учитывается правило рекомендаций при стрессе, связанном с работой. На столбец категории может быть наложен индекс для ускорения выборок при росте объёма данных.
 191|Документация            |Столбец часов сна принимает вещественное число от нуля до двадцати четырёх; столбец минут активности — целое от нуля до тысячи четырёхсот сорока. Оба необязательны. Низкое значение сна усиливает текст предупреждения в рекомендации и увеличивает вклад в риск прогноза. Отсутствие активности при низкой энергии также меняет совет сервера.
 192|Документация            |Столбец времени создания хранит момент фиксации записи с учётом часового пояса; при создании без явной даты подставляется время сервера. Сортировка истории и выбор последней записи для индекса выполняются по убыванию этого поля. Отдельной таблицы пользователей в учебной версии нет: все записи относятся к одному условному владельцу журнала.
 193|Heading 3               |2.2.3 Объектно-реляционное отображение и модуль подключения
 194|Документация            |Класс записи настроения наследует базовый класс декларативного описания таблиц. Атрибуты класса соответствуют столбцам; сессия служит единицей работы: в ней накапливаются изменения, затем выполняется подтверждение транзакции или откат. Схемы проверки данных на входе и выходе отделены от класса таблицы: на создание принимается одна структура, клиенту возвращается другая, включающая идентификатор и время создания, согласованные с базой после подтверждения.
 195|Heading 3               |2.2.4 Жизненный цикл записи в базе данных
 196|Документация            |При создании обработчик строит объект строки, добавляет его в сессию, подтверждает транзакцию и обновляет объект из базы, чтобы вернуть актуальный идентификатор. При чтении списка выполняется запрос ко всей таблице с упорядочиванием от новых к старым. При чтении одной записи — фильтр по идентификатору; если строка не найдена, возвращается ответ «не найдено». При изменении поля присваиваются заново, транзакция подтверждается. При удалении объект исключается из сессии, транзакция подтверждается, клиент получает пустой ответ с кодом успешного удаления без тела.
 197|Документация            |Для прогноза отдельный запрос выбирает не более четырнадцати последних строк; модуль прогноза получает их списком и не обращается к базе напрямую. Такое разделение упрощает тестирование формул по заранее подготовленному набору записей.
 198|Heading 3               |2.2.5 Логическая модель данных
 199|Документация            |Логическая модель предметной области в текущей версии сводится к одной сущности «запись настроения». У сущности восемь содержательных атрибутов помимо идентификатора: три шкалы самочувствия, текстовая заметка, категория, сон, активность и момент создания. Связей «один ко многим» с другими таблицами нет: отзывы о советах на сервере не персистируются, каталог статей советов хранится в коде клиента. Такая простота соответствует учебному характеру проекта и позволяет подробно описать каждый столбец и каждый этап обработки без введения избыточных сущностей.
 200|Документация            |При расширении системы естественными кандидатами на новые сущности были бы «пользователь» и «отзыв о совете», однако в реализованной версии они сознательно опущены, чтобы сосредоточиться на полном цикле ведения журнала и серверной аналитике.
 201|Документация            |Вывод по разделу 2.2. Модель данных минимальна и полностью покрывает журнал мониторинга; операции подтверждения, выборки и удаления согласованы с программным интерфейсом и клиентским слоем доступа к серверу.
 202|Heading 2               |2.3 Моделирование поведения и структуры системы
 203|Heading 3               |2.3.1 Варианты использования
 204|Документация            |Граница системы охватывает мобильный клиент и сервер с базой данных. Единственный актор — пользователь, ведущий дневник самочувствия. Вариант «создать запись» начинается с ввода оценок на клиенте и завершается появлением новой строки в таблице записей после подтверждения транзакции. Вариант «получить историю» предполагает загрузку полного списка с сервера и применение фильтров на устройстве по дате, категории и диапазонам шкал без повторного обращения к серверу для каждого фильтра.
 205|Документация            |Варианты «изменить запись» и «удалить запись» обращаются к адресу ресурса с указанием идентификатора. Вариант «показать индекс благополучия» инициируется клиентом при открытии главной панели: сервер находит последнюю запись, вычисляет взвешенную сумму и возвращает число и ссылку на запись-основание. Вариант «получить рекомендацию» использует ту же последнюю запись, но дополнительно применяет правила текста на русском или белорусском языке интерфейса. Вариант «получить прогноз» учитывает до четырнадцати последних записей; при недостатке данных возвращается пояснение и число уже имеющихся записей без оценки риска.
 206|Документация            |Вариант «настроить интерфейс» не обращается к серверу: язык и тема записываются в локальное хранилище. Вариант «отправить отзыв о совете» передаёт идентификатор совета и текст на сервер для приёма; дальнейшая аналитика отзывов в учебной версии не реализована. Включённые связи между вариантами отражают то, что после создания записи клиент при обновлении главной панели автоматически инициирует запросы индекса и прогноза.
 207|Heading 3               |2.3.2 Сценарий взаимодействия при создании записи
 208|Документация            |Временная последовательность создания записи описывается следующими шагами. Пользователь вводит данные на экране добавления. Экран передаёт параметры службе доступа к серверу. Служба формирует сетевой запрос создания ресурса на адрес журнала. Модуль маршрутов журнала проверяет тело запроса, создаёт объект строки таблицы и передаёт его сессии базы данных. Сессия выполняет операцию вставки в PostgreSQL. После подтверждения транзакции объект обновляется из базы, модуль маршрутов сериализует ответ. Служба на клиенте разбирает текст ответа в объект записи. Экран сообщает об успехе и завершает работу. При следующем показе главной панели клиент снова запрашивает список и прогноз, чтобы отобразить актуальные карточки.
 209|Документация            |Ошибка проверки данных на сервере приводит к ответу с кодом «ошибка клиента» и описанием поля; сетевой сбой обрабатывается на клиенте без изменения базы. Таким образом, критическая точка согласованности — момент подтверждения транзакции в PostgreSQL; до него запись не видна другим запросам.
 210|Heading 3               |2.3.3 Состав программных компонентов
 211|Документация            |На стороне мобильного устройства выделяются компонент экранов, компонент переиспользуемых виджетов оформления, компонент доступа к серверу, компонент моделей данных, компонент локального хранилища параметров, компонент статического каталога советов и компонент конфигурации адреса сервера. Экраны зависят от службы доступа и от хранилища параметров; каталог советов поставляет тексты без обращения к базе.
 212|Документация            |На стороне сервера выделяются компонент приложения веб-фреймворка, компонент маршрутов журнала и учебных маршрутов, компонент сервисов вычислений, компонент схем проверки данных, компонент моделей таблиц и компонент подключения к базе. Маршруты вызывают сервисы при запросах индекса, рекомендации и прогноза; для простого сохранения записи достаточно модели таблицы и сессии. Компонент подключения единственный, кто открывает соединение с PostgreSQL.
 213|Документация            |Между узлами установлена зависимость по протоколу передачи гипертекста: клиентский компонент доступа обращается к компоненту маршрутов; тот — к сервисам и моделям; модели — к компоненту подключения и далее к СУБД. Локальные настройки и советы остаются на устройстве, что уменьшает объём сетевого трафика и упрощает работу при кратковременной недоступности сервера.
 214|Документация            |Вывод по разделу 2.3. Описание вариантов использования, сценария создания записи и состава компонентов согласовано с реализацией в репозитории и дополняет требования первой главы; поведение и структура системы зафиксированы развёрнутым текстом без опоры на отдельные графические листы.
